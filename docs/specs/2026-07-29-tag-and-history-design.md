# Tag 与项目历史设计

## 目标

按照 ironforge 讨论群确认的流程，实现“开发分支上传完成后，在创建 MR 前为关键版本打 Tag”，并让项目历史清楚区分分支提交、Tag 和合并。

## 规则

- 普通上传不创建 Tag。
- Tag 只出现在“提交合并审核”流程中，位于最终确认之前。
- 用户可选择“不建立版本标记”或填写一个不可重复的 Tag 名称和说明。
- 确认交付时，软件先在当前开发分支最新提交上创建并推送 Tag，再创建指向 `main` 的 MR。
- Tag 已存在且指向同一提交时视为已完成，可继续重试 MR；指向其他提交时停止并提示改名。
- 软件不移动或覆盖已有 Tag。

## 历史表现

- 分支提交：蓝色，显示所在工作版本。
- Tag：金色，显示版本标记名称及对应提交。
- MR 已合并：绿色，显示来源分支、目标 `main` 和审核单号。
- 普通本地示例记录：保持灰色。

## 恢复与验证

- MR 草稿保存 Tag 选择和填写内容。
- Tag 成功但 MR 失败时，重新提交不会重复创建 Tag。
- 服务端分别读取 GitLab 的提交、Tags 和已合并 MR，按时间合并排序。
- 测试覆盖 Tag 创建顺序、同提交幂等、重名冲突、草稿恢复和历史分类。
