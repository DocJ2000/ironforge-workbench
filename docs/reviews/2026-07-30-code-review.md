# Ironforge Workbench 代码审查

审查日期：2026-07-30  
审查范围：React 前端、Electron 主进程与 IPC、本地 HTTP 服务、Git/GitLab 工作流、凭据与更新模块。

## 重要发现

### [高] 内嵌登录窗口的证书例外是否可以限定到已登记主机？

- 问题位置：`electron/certificatePolicy.ts`、`electron/main.ts` 的 `certificate-error` 处理。
- 原因：原实现只检查“来自被跟踪窗口且为 HTTPS”，没有确认发生证书错误的主机是否属于该次登录导航。
- 风险：登录窗口若被引导至攻击者控制的 HTTPS 地址，应用可能接受其不受信任的证书，扩大中间人攻击面。
- 改进方案：建议让全局证书处理和独立登录会话共用同一份已登记主机集合，仅对 `ERR_CERT_AUTHORITY_INVALID` 且主机匹配时放行；过期证书和主机名不匹配仍拒绝。
- 修改结果：已收紧并增加恶意主机回归测试。

### [高] 凭据文件损坏时是否应该停止写入而不是当作“尚未配置”？

- 问题位置：`electron/credentialVault.ts` 的 `read()`。
- 原因：原实现将文件不存在、解密失败和 JSON 损坏全部吞掉并返回空对象。
- 风险：用户随后保存设置时可能覆盖仍可人工恢复的加密凭据，造成连接信息不可逆丢失，也掩盖磁盘或 Windows 加密环境异常。
- 改进方案：建议只把 `ENOENT` 解释为首次使用；其他读取错误显示可操作提示并保持原文件不变。
- 修改结果：已区分缺失与损坏，并验证损坏文件不会被覆盖。

### [中] 外部网址解析失败时是否可以稳定返回用户错误？

- 问题位置：`electron/main.ts` 的铁炉堡打开、弹窗处理和主窗口外部链接处理。
- 原因：多个入口直接调用 `new URL()`，格式错误时会同步抛出。
- 风险：IPC 调用可能表现为按钮无反应，窗口打开回调也可能产生未处理异常；非网页协议的安全判断分散且容易遗漏。
- 改进方案：建议集中使用不抛异常的 HTTP/HTTPS 解析函数，所有入口复用。
- 修改结果：已新增 `parseExternalHttpUrl()` 并覆盖非法、文件和脚本协议。

### [中] Git 集成测试是否需要符合 Windows 磁盘环境的时限？

- 问题位置：`server/repositoryPull.test.ts`。
- 原因：测试需要创建两个仓库、提交并推送，但沿用 Vitest 默认 5 秒时限；同步盘或杀毒扫描会让正常流程偶发超时。
- 风险：发布流水线出现假失败，真实回归容易被误判为环境波动。
- 改进方案：建议仅为两个 Git 集成测试设置 15 秒上限，不提高全局单元测试时限。
- 修改结果：已调整，相关测试稳定通过。

### [中] 超大页面组件是否可以按领域职责拆分？

- 问题位置：`src/features/delivery/DeliveryPage.tsx`、`src/features/tasks/ProjectUploadPage.tsx`、`src/features/account/AccountPage.tsx`。
- 原因：页面同时负责数据加载、草稿恢复、业务转换、网络动作和多步骤渲染；辅助函数还与组件共同导出。
- 风险：状态组合增长后更容易出现返回页面丢失、失败重试覆盖状态及局部修改引发整页回归，测试也需要大量环境准备。
- 改进方案：建议本轮只抽离上传分支规则、状态展示和共享向导布局，保持 API 与数据格式不变；不进行一次性大重写。
- 修改状态：将在 UI 重设计任务中实施。

## 优点

- Electron 主窗口已启用 `contextIsolation`、`sandbox`，并关闭 `nodeIntegration`。
- Git 命令使用 `execFile` 与参数数组，未发现字符串拼接执行造成的命令注入。
- 本地 HTTP 服务只监听 `127.0.0.1`，写操作还校验同源请求。
- 删除本地项目只允许带有软件管理标记的目录，避免误删用户自行添加的工程文件夹。
- 凭据使用 Windows `safeStorage` 加密，前端只能读取脱敏状态。
- 上传失败已经保留本地提交并提供单独重试入口，业务方向正确。
- 测试覆盖了提交、分支、LFS、MR、项目登记、凭据、更新和主要 React 页面，基础较扎实。

## 建议修改点

1. 完成证书、外部链接、凭据损坏和 Git 测试稳定性修复。
2. 用统一视觉令牌与页面框架降低 CSS 重复和布局漂移。
3. 将项目首页改为行式台账，空态与有项目状态使用不同操作布局。
4. 抽离上传分支规则，明确草稿保留、主动退出和失败重试状态。
5. 简化账户、历史、错误和更新区域，并补齐高风险流程测试。
6. 通过多尺寸截图、全量测试、构建和公开发布审计后再判断是否可打包。
