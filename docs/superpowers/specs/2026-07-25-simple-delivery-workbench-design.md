# 傻瓜式交付工作台设计

## 目标

将现有工程师工作台收敛为一个“一页完成”的交付页面。用户不需要理解 Git 命令，只需核对本地改动、选择 Ironforge 交付包和 GitLab MR 审核人，即可发起管理员审核。

页面必须清楚表达两条不同的数据路径：

- GitLab 同步全部有效仓库改动，包括 `source`、`reference`、`output` 和 `charge.json`。
- Ironforge 只发布 `charge.json` 中选中的非空 `output` 包。

管理员在 GitLab MR 中完成审核与合并。创建 MR 即提交 Ironforge 发布申请，MR 合并即完成发布，工程师不再执行第二次发布操作。

## 页面结构

页面顶部显示当前仓库、当前分支和扫描状态。主体按顺序显示两个步骤。

### 1. 同步到 GitLab

系统扫描仓库后展示三个可点击状态标签：

- 文件数量，例如“32 个文件”
- `charge.json` 自动更新
- 临时文件已排除

点击“文件数量”后打开右侧抽屉，按 `source`、`reference`、`output` 和根目录配置分类展示新增、修改、删除文件。该抽屉只用于核对，不提供取消提交功能，避免产生不完整工程提交。

点击“charge.json 自动更新”后展示生成前后的结构化差异。点击“临时文件已排除”后展示被忽略文件及对应规则，包括 `.superpowers`、日志、缓存和工具临时目录。

同步前选择 Ironforge 交付包。系统扫描所有非空 `output/<domain>/<package>` 目录，自动生成候选交付包并默认全部选中。每个包同时支持：

- 勾选或取消，决定是否写入 `charge.json`
- 点击包名打开文件清单

生成 `charge.json` 时保留项目既有结构和字段格式，仅更新由交付包选择控制的内容。

同步分支选择器支持两种操作：

- 选择已有本地分支，默认当前分支。
- 点击新增按钮创建分支，填写新分支名并选择起点，默认从当前分支创建。创建成功后自动选中新分支；第一次 push 后该分支才出现在远端 GitLab。

同步确认中可以选择是否创建版本 Tag。Tag 用于标记需要长期保留的阶段版本，不要求每次同步都创建：

- 普通阶段版本采用 `<阶段>-v<序号>`，例如 `T2-v1`、`T2-v2`。
- 确认的最终阶段版本可以使用 `T0`、`T1`、`T2`。
- 修模等特殊版本允许使用 `T2-修模-v1` 或自定义名称。
- 同一个 Tag 名只能指向一个提交。系统在 Commit 前同时检查本地和远端 Tag；若名称已存在，只允许更换名称，不提供覆盖或强制移动。
- 同步执行顺序为 Commit、push 分支、创建 annotated Tag、push Tag。分支 push 成功但 Tag push 失败时，只重试 Tag，不重复 Commit。

### 2. 提交 Ironforge 发布审核

审核人列表通过 GitLab 项目成员接口实时加载，显示头像、姓名、GitLab 用户名和项目角色。

- 至少选择一位审核人后才允许提交。
- 管理员和最近使用过的审核人排在前面。
- 胡庆磊作为已知管理员显示在推荐位置，但系统不得未经用户确认自动选中。
- 支持按姓名或 GitLab 用户名搜索。
- 选择结果必须作为 Reviewer 写入真实 GitLab MR。

MR 信息不再复用 Git 同步注释。第二步提供独立的 MR 标题和 MR 说明：

- MR 标题使用普通文本。
- MR 说明使用 GitLab Flavored Markdown，提供标题、粗体、列表、引用、链接和预览工具，不发送任意 HTML。
- 支持粘贴飞书云文档链接；链接权限仍由飞书控制，工作台不复制文档内容或改变权限。
- 支持选择 PDF 和常见图片作为附件。文件先保留在本地待上传列表，用户确认创建 MR 后才通过 GitLab Project Markdown Uploads API 上传，再将返回的 Markdown 链接插入 MR 描述。
- 上传进度和单个附件失败原因必须可见。任一必需附件上传失败时不创建 MR，允许移除或重试失败附件。

第一步先创建或选择要同步的本地分支，再提供独立主操作“同步到 GitLab”。点击后打开确认弹窗，要求填写必填的“同步注释”，并展示分支、文件数量和可选版本 Tag。该注释作为 Git Commit message；用户确认后执行分支切换、Commit、push，以及用户明确选择的 Tag 创建与 push，不选择审核人，也不创建 MR。

同步成功后解锁“提交发布审核”。此时再选择审核人和目标分支；用户单独确认后调用 GitLab 创建 MR。该 MR 就是 Ironforge 发布申请，不再显示独立的发布按钮或要求第二份发布注释。同步失败不会进入 MR 阶段，MR 创建失败也不会重复 Commit 或 push。

## 交互规则

状态标签和可选择项使用不同的视觉语义：

- 状态标签可点击查看详情，但不能改变提交范围。
- output 交付包使用复选框，可以改变 Ironforge 发布范围。
- 审核人使用复选框，可以改变 MR Reviewer。

GitLab 同步前展示确认摘要，包含所选分支、有效改动数量、同步注释和可选 Tag。用户确认后，系统依次完成切换分支、本地提交、推送分支和可选 Tag 推送。审核人与 MR 信息仅出现在后续“创建 MR”区域。

MR 页面与状态提示应明确表达：等待管理员审核、审核通过以及合并后已发布。

任何 `git commit`、`git push`、创建或重开 MR、合并 MR 操作都必须在执行前获得用户明确确认。扫描、预览和本地生成候选 `charge.json` 不属于远端操作。

## 数据流

1. 仓库扫描器读取 Git 状态、当前分支和有效文件变化。
2. output 扫描器读取非空交付包目录并形成候选包列表。
3. charge 生成器根据已选包构造候选 `charge.json`，供用户预览。
4. GitLab 成员服务读取项目成员，形成审核人列表。
5. 用户创建或选择同步分支，点击“同步到 GitLab”，在弹窗中填写同步注释并按需选择版本 Tag。
6. 用户明确确认后，后端切换至所选分支，执行提交和推送；选择 Tag 时再创建并推送 annotated Tag。
7. 同步成功后，用户填写独立 MR 标题和 Markdown 说明、添加飞书链接或附件、选择审核人与目标分支。
8. 用户单独确认创建 MR；后端先上传待处理附件，再通过 GitLab API 创建 MR，写入 Reviewer 和完整说明。
9. 工作台轮询 MR 审核与合并状态；MR 合并后显示 Ironforge 已发布。

各模块保持独立接口：仓库扫描器不负责生成 charge，charge 生成器不调用 GitLab，MR 服务负责提交发布审核但不绕过 GitLab 管理员审批。

## 状态与异常

- 仓库存在冲突、游离 HEAD 或未配置远端时，停止提交并给出具体修复提示。
- 没有有效改动时，禁用创建 MR，并提示“没有需要提交的内容”。
- output 没有非空包时，允许仅同步 GitLab，但禁用提交 Ironforge 发布审核。
- GitLab 成员加载失败时，不允许以空审核人绕过；提供重试和打开 GitLab 的入口。
- charge 生成失败时保留原文件，不写入半成品。
- push 成功但 MR 创建失败时，不重复提交或推送，只重试创建 MR。
- 新建分支名称不合法、与现有分支冲突或无法安全切换时，不修改当前分支和工作区。
- Tag 名称不合法或已存在时，在 Commit 前阻止同步；Tag push 单独失败时保留已推送分支并提供仅重试 Tag。
- 飞书链接格式不合法时提示修正，但不主动请求文档内容或权限。
- PDF 或图片附件超过 GitLab 限制、类型不支持或上传失败时，不创建内容不完整的 MR。
- MR 被关闭、要求修改、审核通过或合并发布时，页面展示对应状态和下一步操作。

错误信息使用用户能执行的语言，展示“发生了什么、哪些动作已完成、下一步怎么办”，不直接暴露原始堆栈。

## 凭据与多用户

GitLab、SSH 和 Ironforge 凭据由当前系统用户单独配置，不写入仓库，不进入前端构建产物。切换使用者时可更换 SSH Key、GitLab 登录信息和 Ironforge 凭据。

前端只显示凭据是否可用和当前身份，不读取或回显密码、私钥内容。

## Windows 桌面交付

最终产品交付为 Windows `.exe`，用户不需要预先安装 Node.js、npm、Git 或 Git LFS。桌面程序使用 Electron 承载现有 React/Vite 界面，并在应用资源中携带经过版本锁定的 PortableGit 与 Git LFS。

所有 Git 子进程必须使用应用内置的 Git 可执行文件，不能依赖系统 `PATH`。SSH Key、GitLab 凭据和 Ironforge 凭据按当前 Windows 用户隔离保存，私钥和密码不得被打包进安装程序。

安装包构建过程可以使用开发依赖，但安装后的运行环境不得要求用户另外安装依赖。发布产物应包含版本信息、文件校验值和可重复构建说明。

## 工程保护与验证

开发和自动化测试不得在真实 `lens-mechanics` 工程目录中执行写操作。单元测试、集成测试和端到端测试必须使用临时目录中的模拟 Git 仓库以及伪造的 GitLab/Ironforge 服务。

在用户现场确认之前，真实工程仅允许执行只读扫描。Commit、push、Tag、附件上传和 MR 创建的真实联调留到用户在场时进行，并继续遵守逐次确认规则。

## 测试

单元测试覆盖：

- 有效文件和排除文件分类
- 非空 output 包扫描
- 交付包选择到 `charge.json` 的映射
- 至少一位审核人的校验
- 提交、push、Tag、MR 创建和合并发布的状态转换
- 新分支名称与版本 Tag 唯一性校验
- MR Markdown 说明、飞书链接和附件列表组装

集成测试覆盖：

- 扫描到创建 MR 的完整成功路径
- push 成功但 MR 创建失败后的重试
- 分支 push 成功但 Tag push 失败后的仅 Tag 重试
- 附件全部上传成功后才创建 MR
- 审核未通过时禁止发布
- 审核通过后只发布 `charge.json` 中的包
- 项目成员加载失败和凭据失效

浏览器测试覆盖桌面和移动宽度，验证抽屉、复选框、搜索、确认对话框和长文件名不会重叠或改变布局。

桌面打包测试还需验证：

- 在未安装系统 Git、Node.js 和 npm 的干净 Windows 环境中启动。
- 应用实际调用内置 Git 与 Git LFS。
- 安装、升级和卸载不会修改用户工程文件。
- 模拟仓库可以完成扫描、charge 预览、新建分支、Commit、push、Tag 和 MR 创建流程。

## 不在本阶段范围

- 采购人员和审核人员的完整独立工作台
- 在前端中直接合并 MR
- 任意编辑 Git 提交文件范围
- 绕过 GitLab 审核直接发布 Ironforge
- 自动保存或传输明文密码和 SSH 私钥
