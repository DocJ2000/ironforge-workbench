# Ironforge Workbench UI 重设计与代码审查规格

## 目标

将桌面应用重构为面向非计算机专业工程师的“项目台账”。用户先找到项目，再进入上传、下载和历史记录，避免在首页同时理解 Git、分支、提交和 MR。

本轮同时审查逻辑正确性、安全性、性能、可维护性和测试完整性。只修复有实际风险的问题，不进行与目标无关的架构重写。

## 用户与任务

主要用户是一台电脑对应一名工程师。用户可能同时维护多个项目，但不了解 Git 术语。

首页的唯一任务是回答：

1. 这台电脑已连接哪些项目？
2. 哪个项目需要处理？
3. 如何打开目标项目？

进入项目后的唯一任务是选择：

- 上传我的修改
- 获取服务器内容
- 查看操作历史
- 在 GitLab 查看本项目

## 信息架构

左侧导航保留两个一级入口：

- GitLab
- 铁炉堡

账户与连接固定在左下角。GitLab 首页不显示全局项目选择器。

### GitLab 项目列表

有项目时，每个项目显示：

- 项目名称
- 本地文件夹
- 当前工作版本
- 本地修改数量
- 最后一次同步时间
- 状态：正常、待上传、上传失败、需要处理

项目行本身是唯一的进入入口。刷新、下载新项目、找到本机项目放在页头工具区。

无项目时，页面中央显示两个明确动作：

- 从公司服务器下载项目
- 添加电脑里已有的项目

### 项目操作页

项目名称、路径和状态集中显示一次。主区域提供上传、下载、历史三个操作入口；GitLab 网页链接作为辅助命令，不与主要任务竞争。

### 上传向导

顺序固定为：

1. 确认项目
2. 核对修改
3. 选择交付包
4. 生成并核对 `charge.json`
5. 选择或创建工作版本
6. 填写上传标题和描述
7. 确认上传
8. 展示 GitLab 提交页面，并选择是否创建 MR
9. 核对 MR 对应的交付文件
10. 填写交付标题、备注和审核人
11. 确认创建 MR
12. 展示 GitLab MR 页面

`main` 只作为 MR 目标，不允许直接推送。分支列表优先读取远端；新项目只有 `main` 时允许以 `main` 为起点创建工作版本。

用户切换一级页面时保留草稿。用户主动点击“返回项目操作”时明确提示并清空当前草稿。推送失败后保留本地提交和重试入口。

## 视觉系统

方向名称：精密工坊。

### 色彩

- 炭黑 `#20262c`：导航和高对比文本
- 工程灰 `#edf0f2`：应用背景
- 白色 `#ffffff`：工作表面
- 动作红 `#d7462f`：主要提交动作
- 信息青 `#167d93`：链接、帮助和进行中状态
- 通过绿 `#237a57`：成功状态
- 警告琥珀 `#a96513`：需要注意但不阻断

颜色必须表达状态或操作类别，不作为无意义装饰。

### 字体与密度

中文正文使用系统中文 UI 字体，数字、提交 ID、分支和路径使用等宽字体。标题层级克制，项目页不使用营销式大标题。

项目列表和文件列表采用完整宽度的行式布局。卡片只用于项目条目、对话框和独立工具，不嵌套卡片。

### 标志性元素

项目状态使用“工程状态轨”呈现：一条细轨同时编码本地修改、远端同步和 MR 状态。它只出现在项目条目与项目详情页，成为产品的识别元素。

### 响应式规则

- 宽窗口：内容最大宽度随窗口扩展，列表利用可用高度。
- 中等窗口：减少左右留白，保持行式项目列表。
- 窄窗口：侧栏变为抽屉，项目元数据换行，底部操作区不遮挡内容。
- 所有固定格式控件使用稳定高度，加载和状态变化不引发布局跳动。

## 文案规则

界面优先使用用户能观察到的结果：

- Push：上传到公司服务器
- Pull：获取服务器内容
- Branch：工作版本
- Commit title：本次更新标题
- Tag：本次交付标签
- Merge Request：提交审核

专业术语只在“专业显示”或帮助说明里补充。错误消息包含：

1. 哪一步失败
2. 已经完成到哪里
3. 文件是否有变化
4. 用户下一步可以点击什么

## 状态与错误恢复

- 页面切换：自动保存未完成向导。
- 主动退出：确认后清空对应项目的草稿。
- 本地提交成功、远端上传失败：显示提交 ID、失败原因和“重新上传”。
- 分支不存在：重新读取远端分支，允许创建新工作版本，不静默回退。
- Git LFS 失败：区分网络、证书、服务器和对象上传错误。
- 更新下载：始终显示检查、下载、等待安装和失败状态。
- 空白页或外部登录失败：保留关闭、重试和系统浏览器打开入口。

## 代码审查范围

审查顺序：

1. 上传、下载、分支、提交、MR 和更新流程的边界条件
2. Electron IPC、外部 URL、凭据、文件路径和命令参数的安全边界
3. Git 历史、项目扫描和轮询的资源占用
4. 超大页面组件、重复状态和不清楚的领域命名
5. 高风险流程的单元与端到端覆盖
6. 仅处理会妨碍维护的样式问题

每个发现记录位置、原因、风险与改进方案。修改应保持现有数据格式兼容，避免覆盖用户配置或工程文件。

## 测试与验收

自动化测试至少覆盖：

- 无项目、有项目和多个项目首页
- 项目刷新后状态更新
- 页面切换保留草稿
- 主动返回清空草稿
- 新项目仅有 `main` 时创建工作版本
- 本地提交成功但推送失败后的恢复
- `charge.json` 对任意 `output` 一级类型目录的生成
- MR 目标固定为 `main`
- 凭据不进入浏览器存储、日志和公开安装包
- 更新说明仅展示跨过的版本

视觉验收至少覆盖 1440×900、1920×1080 和 760px 窄窗口。检查文本溢出、遮挡、空白浪费、键盘焦点和减少动画设置。

完成标准：

- 全量测试、类型检查、lint 和公开发布审计通过
- 关键页面截图无重叠、截断和明显空白失衡
- 不修改用户工程项目
- 不将个人、公司或项目数据写入公开源码和安装包
